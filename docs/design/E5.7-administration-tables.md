## How the rights are worked out
1. Roles of the user = direct roles (`user_role`) + roles of all enabled groups the user is in (`user_group_member` -> `user_group_role`).
2. User permissions = union of the permissions of those roles.
3. If the request comes from a registered workstation whose workstation group has a non-empty allowed list:
   effective permissions = user permissions AND that list. Empty list or office mode = no restriction.
4. Checked on the server for every request (the menu only follows what the server reports in `/api/auth/me`).
5. Changing a role, a group or a workstation group signs the affected users out (existing mechanism) so they get the new rights.

## How a parameter value is found
WORKSTATION value, else WS_GROUP value of its group, else SITE value, else GLOBAL value, else the default of the
definition. A value is only accepted for a scope the definition allows and within its type / min / max / choices.
The screen shows the effective value and where it comes from. Seeded parameters: session timeout, password minimum
length, lockout attempts, lockout minutes, audit retention days.

## Decisions I propose (please confirm or change)
1. Roles and permissions stay global (no `site_id`), as today; only the new group / workstation / parameter-value tables carry `site_id`.
2. GLOBAL parameter values have `site_id` empty (they belong to no single site); all other scopes carry it.
3. Default grants of the new permissions: ROLE_MANAGE -> SUPER_ADMIN only; WORKSTATION_MANAGE -> SUPER_ADMIN, ADMIN;
   PARAMETER_VIEW -> SUPER_ADMIN, ADMIN; PARAMETER_EDIT -> SUPER_ADMIN only.
4. User groups are managed with the existing USER_MANAGE permission (no extra permission).
5. The workstation token is an HttpOnly cookie set by the server when an administrator registers the browser (scripts cannot read it);
   only its SHA-256 hash is stored. One registered browser per workstation: registering again replaces the old one.
6. Audit retention days is only a parameter in E5.7; the job that deletes old audit rows is not part of it.
7. Lockout attempts / minutes and password minimum length may be set for GLOBAL or SITE only; session timeout also per workstation group and workstation (e.g. a shorter one on kiosks).
